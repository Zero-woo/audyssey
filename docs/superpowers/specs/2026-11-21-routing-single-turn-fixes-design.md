## 1. 왜 하는가

- 대화 이력을 쓰는 multi-turn 라우터로 넘어가기 전에, 한 문장 단위(single-turn)에서 남은 오답부터 고칩니다.
- 대상 구성은 작은 모델 최고 구성인 `hybrid`(H2O-4B 결정 모델 + Qwen2.5-3B 값 채우기) + 가드레일입니다. dev macro-F1은 0.906이고, 73문제 중 13문제를 틀립니다(`evals/routing/runs/2026-11-19_hybrid-h2o-qwen2.5-3b-guard-dev`).
- 시연 구성(Gemini, tools, 설명 v3)은 dev와 test 모두 1.000이라 이번 작업의 대상이 아닙니다. 다만 4단계에서 설명 파일을 바꾸면 Gemini도 다시 확인합니다.

## 3. 목표, 비목표, 실패 조건

- **목표:** 위 오답을 줄이되, 맞던 문제를 망치지 않습니다. 각 단계는 4.5절의 채택 규칙을 통과해야 들어갑니다.
- **비목표**
  - 대화 이력(multi-turn)
  - 되묻기 카드의 후보 버튼. `contracts.py`의 `Clarify`를 바꿔야 해서 multi-turn 단계로 미룹니다.
  - 복합 요청을 나눠서 제안하기. 요청을 쪼개려면 LLM을 한 번 더 불러야 합니다.
  - 결정 모델 교체나 fine-tuning
- **실패 조건 (안 되는 것)**
  - dev에 맞춰 기준값이나 문구를 고르는 것. 기준값은 train으로만 정합니다.
  - 되묻기를 남발해서 맞던 명령이 되묻기로 바뀌는 것
  - 핵심 파일(`contracts.py`, `graph.py`, `api.py`, `settings.py`)을 고치는 것. 이번 범위는 이 파일들 없이 끝나야 합니다.

## 4. 설계

### 4.0 지금 구조

- `src/audyssey/tools/routing/hybrid.py`의 `_ask()`는 결정 서버 `POST <url>/v1/systemone`에 요청 문장, 작업 요약과 함께 질문 3개를 보냅니다(`_questions()`).
  - `decision` (객관식): 선택지 14개. 명령 8개, `clarify_<이유>` 5개, `none` 1개.
  - `target` (객관식): 작업의 소스 목록과 `residual`
  - `residual_stem` (예/아니오, `noul`)
- 서버는 객관식마다 `choice`와 함께 선택지별 `probabilities`, `confidence`를 돌려줍니다(`runs/2026-11-18_h2o-lightning-4b-dev/answers.jsonl`에서 확인). 그런데 `_ask()`는 지금 `choice`와 `noul`만 남기고 확률은 버립니다.
- 되묻는 문장은 결정 모델이 쓰지 않습니다. `QUESTIONS`에 이유별 고정 문장이 있고, 이번에도 그대로 씁니다.
- 서버의 `choice`는 항상 확률 1위입니다(dev 저장본 146개 답에서 모두 일치).

### 4.0.1 측정 방식 (1–2단계 공통)

- 먼저 `_ask()`가 서버 응답 전체(확률 포함)를 실행 폴더에 남기게 합니다 **(제안)**. 그다음 새 질문을 넣은 상태로 train과 dev를 한 번씩 돌립니다.
- 기준값 탐색은 저장된 확률로 오프라인에서 합니다. 기준값마다 서버를 다시 부르지 않습니다.
- 기준값은 "이 문제를 되물어야 하나"를 맞히는 이진 판정으로 고릅니다 **(제안)**.
  - train 95문제 전체를 씁니다. 정답이 해당 되묻기인 문제가 양성이고, 나머지는 모두 음성입니다.
  - train의 양성은 복합 요청 4개, 대상 모호 몇 개뿐입니다. 그래서 "맞히기"보다 "음성을 잘못 막지 않기"를 우선합니다. 판정 F1이 가장 높은 값을 고르고, 같으면 오탐이 적은 쪽을 고릅니다.
- **건너뛰는 조건:** 어떤 기준값도 train 오답을 줄이지 못하면 그 단계는 넣지 않고 결과만 기록합니다. train에서 좋아 보여도 dev에서 4.5절 규칙을 통과하지 못하면 넣지 않습니다.
- 이번에는 train 문제를 새로 만들지 않습니다 **(제안)**. 평가셋을 고정해 두어야 이전 결과와 비교할 수 있습니다.

### 4.1 1단계: 복합 요청 질문 추가

- `_questions()`에 예/아니오 질문 `composite`를 추가합니다. 질문 문장은 "요청(request)에 서로 다른 편집이 둘 이상 들어 있나요?"입니다 **(제안: 문구)**.
- `route()`에서는 이 질문의 `noul`이 기준값 `τ_c` 이상이면 decision 답과 상관없이 `clarify(composite)`를 냅니다. 다만 decision이 `none`이면 그대로 둡니다 **(제안)**.
- `τ_c`는 4.0.1의 방식으로 0.3–0.9 범위를 0.1 간격으로 훑어 고릅니다.
- 결정 서버 호출은 그대로 한 번입니다.

### 4.2 2단계: 대상 모호 판단

- `_ask()`가 `target`의 `probabilities`를 남기게 합니다.
- 대상이 필요한 명령(`keep`, `drop`, `set_gain`, `set_pitch`, `reseparate`, `generate`)일 때만 적용합니다. 1위와 2위 확률 차이가 기준값 `τ_t`보다 작으면 `clarify(ambiguous_target)`를 냅니다.
- `τ_t`는 4.0.1의 방식으로 0.05–0.5 범위를 훑어 고릅니다. 양성은 정답에 `clarify(ambiguous_target)`가 들어 있는 문제입니다. g-067처럼 두 이유를 모두 허용하는 문제도 양성입니다.
- 1단계와 2단계가 함께 걸리면 복합 요청 쪽이 이깁니다 **(제안)**. 대상을 정하기 전에 요청을 나눠야 하기 때문입니다.

### 4.3 3단계: 소스 이름표와 residual 설명

- `_questions()`의 `target` 선택지 문장에 출처를 붙입니다.
  - 지금: `dog barking (sfx, 꺼짐)`
  - 바꾼 뒤: `dog barking (sfx, 원본 분리, 꺼짐)`, `dog barking (generated) (sfx, 생성: s1 대체, 켜짐)` **(제안: 문구)**
  - 근거는 `Source.origin`, `Source.replaces`입니다.
- residual 선택지 문장 "분리되지 않고 남은 나머지 소리"에 사용자가 쓰는 표현("나머지 소리", "남은 소리", "분리 안 된 소리")을 넣습니다 **(제안: 문구)**. 이 문구는 train 실패 문장을 그대로 베끼지 않습니다(4.4의 6글자 규칙과 같은 기준).
- 이 단계는 기준값이 없습니다. 문구 후보가 여럿이면 train으로 고릅니다.

### 4.4 4단계: 설명 자동 개선 루프

- **대상:** Qwen2.5-3B `real` 라우터(tools, 설명 v3, 가드레일 끔)입니다. 개선 근거는 train 실패만 씁니다.
- **새로 만들 것**
  - `src/audyssey/routing_improve.py`
  - CLI `audyssey improve-routing`
- **고칠 것:** 라우터와 평가가 설명을 고정 파일 대신 인자로도 받게 합니다.
  - 대상: `real._commands()`, `hybrid`의 설명 사용처, `routing_eval`의 `DESCRIPTIONS` / `_descriptions()` / 캐시 키
  - 인자가 없으면 지금처럼 `descriptions.json`을 읽습니다.
  - 캐시 키는 받은 설명의 sha로 만듭니다.
- **회차마다 하는 일 (최대 5회)**
  1. 현재 설명으로 train을 k=1로 돌려 오답을 모읍니다. 각 오답에는 요청, 소스 목록, 정답, 라우터 답이 들어갑니다.
  2. 개선용 LLM에 현재 설명 JSON과 train 오답만 주고, 같은 모양의 설명 JSON을 받습니다.
     - 개선용 LLM은 Gemini이고, OpenAI 호환 주소로 부릅니다.
     - 출력은 `response_format: json_schema`로 강제합니다.
     - 비용이 드므로 실행 전에 따로 승인을 받습니다.
  3. 코드 검사를 통과하지 못하면 그 회차의 후보를 버립니다.
     - 명령과 필드(`when`, `instead`, `params`, `examples`)가 모두 있어야 합니다.
     - 명령마다 400자 이하여야 합니다.
     - train 오답 요청과 6글자 이상 연속으로 겹치면 안 됩니다.
     - `instead`에 부정 명령문("~하지 마", "마세요")이 있으면 안 됩니다.
  4. dev를 k=1로 돌려 4.5절 채택 규칙으로 판단합니다. 통과하면 다음 회차의 기준이 됩니다.
- **결과물:** 회차별 기록(후보 설명, train 오답, dev 지표, 채택 여부)을 `evals/routing/runs/<날짜>_improve-qwen2.5-3b/round-N/`에 남깁니다.
- **마무리**
  - 최종안을 `descriptions.json`에 쓰고 `version`을 올립니다.
  - hybrid도 같은 설명을 쓰므로, hybrid + 가드레일 dev와 Gemini dev(tools)도 4.5절 규칙으로 확인합니다. 둘 중 하나라도 통과하지 못하면 `descriptions.json`에 쓰지 않고 결과만 기록합니다 **(제안)**.
  - 값 없음(c-069) 오답은 이 단계에서만 다룹니다. hybrid의 선택지 문장이 설명의 `when`과 `instead`로 만들어지기 때문입니다. 고쳐지지 않을 수도 있습니다.
  - 회차마다 dev로 채택하므로 dev에 간접적으로 맞춰질 수 있습니다. 이 점은 spec 6절이 "dev 최고 회차를 고른다"로 받아들인 부분입니다. test는 마지막에 한 번만 열어 이를 확인합니다.
  - 비교군은 수동 수정 v2 → v3(`docs/manual_edits.md`, dev 0.553 → 0.625)입니다.

### 4.5 채택 규칙 (모든 단계 공통, 실행 전에 고정)

- dev macro-F1이 올라야 합니다.
- 어느 명령의 dev recall도 3%p 넘게 떨어지면 안 됩니다.
- none suppression(`routing_eval.metrics()`의 `none_suppression`: 정답이 `none`인 문제에 `none`으로 답한 비율)이 떨어지면 안 됩니다.
- 1–3단계는 가드레일을 끈 점수(모델 실력)와 켠 점수(시스템)를 둘 다 기록하고, 채택 판단은 켠 점수로 합니다 **(제안)**. 4단계는 끈 점수로 판단합니다(실험 보고서의 원칙).
- 신뢰구간이 넓어서(dev template 31개) 작은 차이는 구분되지 않는다는 점을 보고서에 함께 적습니다.

### 4.6 test

- 모든 단계가 끝난 뒤 최종 구성마다 test를 한 번만 엽니다. 최종 구성은 hybrid + 가드레일, 그리고 개선된 설명을 쓴 Qwen2.5-3B `real`입니다.
- 기록은 `test_opens.jsonl`에 남습니다. 모델당 최대 3회이고, Qwen2.5-3B는 이미 1회를 썼습니다.

## 5. 접근 방식 비교

| 방식 | 내용 | 판단 |

## 8. 구현자에게 맡기는 것

- 예/아니오 질문과 선택지 문구의 세부 표현. 단, 후보는 train으로 고릅니다.
- 기준값 탐색 스크립트의 형태. 저장된 확률을 다시 쓰므로 서버를 다시 부르지 않게 만들어도 됩니다.
- 개선용 LLM 프롬프트의 세부 문장. 단, 4.4의 금지 규칙은 코드 검사로 지킵니다.

## 9. 검토할 위험 (Review Focus)

- **"A는 두고 B만 빼줘" (x-052)를 복합 요청으로 오인:** 편집은 하나입니다. 1단계 뒤에도 맞아야 합니다.
- **대상이 하나뿐인 작업에서 확률이 분산되는 경우:** 예를 들어 소스 2개와 residual 사이에서 확률이 갈릴 수 있습니다. 2단계가 이런 경우에 되묻기를 남발하지 않는지 train에서 확인합니다.
- **`render`, `add_source`처럼 대상이 없는 명령:** 2단계 규칙이 걸리면 안 됩니다.
- **설명 파일 변경이 hybrid 선택지 문장에도 반영되는 점:** 4단계 채택 뒤 hybrid dev를 다시 봅니다.
- **캐시 키:** 지금 `_cache_file`의 키에는 결정 서버에 보내는 질문 내용이 들어가지 않습니다. 1–3단계는 질문이 바뀌므로 질문 내용의 해시를 키에 넣습니다 **(제안)**. 그러면 hybrid 캐시가 한 번 무효화되는데, 다시 돌리는 비용은 로컬 GPU 몇 분입니다.
